# 개발 방향

## 판단 기준

프로젝트의 가치는 동일 조건에서 전략 변경의 효과와 회귀를 검증하는 데 있다. 코드 구현과 실측 실행 가능성이 확보됐으므로 다음 작업은 비교 결과의 신뢰도와 과제의 대표성을 높이는 순서로 진행한다. 기능 수나 한 번의 좋은 결과를 진척 기준으로 삼지 않는다.

[18회 통합 실측](live-benchmark.md)에서는 Graph의 paired 도구 호출 수가 줄었지만 총 토큰·시간은 늘었다. F1 차이에는 추가 근거 수와 경로/관계 표기가 영향을 줬다. 따라서 현재의 우선순위는 Graph 우위 홍보나 기능 확장보다 채점 계약과 실험 조건의 신뢰도를 높이는 것이다.

## 1. 관측과 비교의 신뢰도

현재 Codex adapter가 보존하는 실패·usage·provenance 계약을 다른 adapter에도 적용한다. 특히 부분 usage, 실제 모델 변경, Graph 도구 오류의 분류를 공통 fixture로 검증한다. 더 세분화된 metric별 unknown 상태는 additive schema version과 함께 도입한다.

host context는 현재 fingerprint와 제한 공개 수준이다. 지원되는 CLI 격리 방법이나 외부 실행 환경을 검증하여 전역 skill/config와 filesystem 읽기 범위를 더 명확히 통제한다. 인증 파일을 복제하거나 개인 로그인을 공유하는 방법은 사용하지 않는다.

완료 기준: 다른 설정·불완전한 사용량·잘못 제공된 도구가 정상 pair로 들어가는 재현 사례가 회귀 테스트에서 차단되고, 결과에서 비교 조건을 확인할 수 있어야 한다.

## 2. 데이터셋과 채점

현재 loglens의 3개 과제는 연결·회귀 검사에 유용하지만 코드베이스 이해 전반을 대표하지 않는다. lookup, 호출 흐름, 구현체/DI, 영향 범위, 근거가 없는 질문을 구분하고 서로 다른 저장소와 크기의 고정 commit을 추가한다.

채점은 필수 근거와 허용 가능한 추가 근거의 관계를 먼저 정의한다. grader v1은 그대로 유지하고, 변경은 dataset/grader version을 올려 사전에 고정한다. 실측 답변에 맞춰 정답을 사후 확장하지 않는다.

경로의 줄 번호, 관계 endpoint의 설명 문자열처럼 이번 실측에서 드러난 표기 차이는 다음 버전의 canonical evidence 계약으로 정리한다. 예를 들어 paths는 저장소 상대 경로, 관계 endpoint는 설명 없는 식별자로 규정하고 두 전략에 같은 안내를 제공한다. 정규화 범위를 검토하고 대표 fixture로 검증한 후 새 버전으로 재측정한다.

완료 기준: 과제 유형별 점수·실패율·토큰·시간을 분리해 보고하고, 특정 과제의 정답 범위나 장황함이 전체 F1 차이를 설명하는지 확인할 수 있어야 한다.

## 3. 전략 최적화

입력 token을 공통 instruction, 도구 schema/설명, source/graph 결과로 분해할 수 있는 관측 수단을 먼저 확보한다. 실제 병목이 확인된 뒤 Graph 결과 크기, 요청 유형 선택, 불필요한 재탐색을 줄인다. 변경마다 동일 버전의 task와 사전에 정한 순서로 paired 실험을 실행한다.

정확도 개선은 F1 하나로 결론내리지 않는다. 필수 근거 recall과 실패율을 함께 확인하고, 비용 미관측 상태에서 token 절감률을 금액 절감률로 바꾸지 않는다. 토큰·시간 차이가 반복·과제 유형을 바꿔도 유지되는지 검증한다.

완료 기준: 필요한 근거를 유지하면서 입력·시간이 개선되는 조건과 개선되지 않는 조건을 함께 설명할 수 있어야 한다.

## 실험 운영

3개 과제 × 3 paired 반복은 현재의 통합 smoke 기준이다. 충분한 통계적 표본이라는 뜻은 아니다. 더 큰 실험은 과제 구성·예산·중단 기준·비교 지표를 미리 정하고 실행한다. run 누락과 실패도 저장하며, 좋은 결과만 골라 성능 주장에 사용하지 않는다.
